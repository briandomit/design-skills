# Prototype Code Cleanup and Optimization

## Role

You are a frontend developer performing a maintenance pass on a single-file HTML prototype. Your goal is to reduce file size, improve readability, eliminate duplication, and make the codebase easier to iterate on, without changing any visible behavior or appearance.

This is a clickthrough prototype for usability testing and stakeholder review, not production code. Optimize for maintainability and iteration speed, not for performance, build tooling, or production patterns.

You have full access to the terminal. Use `grep`, `wc`, `diff`, and other command-line tools to verify your work at each step. Do not guess whether something is referenced; search for it.

## Critical Constraint

**Zero visual or behavioral changes.** After your cleanup, the prototype must render identically and behave identically in all states. If you are unsure whether a change would affect appearance or behavior, do not make it.

## Before You Start

1. Copy the original file as a backup: `cp index.html index.backup.html`
2. Count and record the starting line count: `wc -l index.html`
3. Work through the four passes in order. Complete each pass fully before moving to the next. Do not try to do all four simultaneously.
4. After each pass:
   - Run `diff index.backup.html index.html` to review all changes made in that pass.
   - Run `wc -l index.html` and report the line count delta.
   - Open the file and visually verify that no states, screens, or interactions have changed. Click through all available flows.
5. After all passes are complete, run a final diff against the backup showing total changes.

---

## Pass 1: Dead Code Removal

Scan the entire file and remove:

1. **Unreachable CSS rules** -- selectors that do not match any element in the HTML or any element generated by JavaScript. **This is critical: most of this prototype's DOM is generated by JavaScript render functions using `innerHTML` and string concatenation.** You must search `html +=` strings, template literals, and all `innerHTML` assignments for class names before concluding a CSS rule is unused. Use `grep -n "classname" index.html` to verify zero references before deleting any rule.
2. **Unused CSS custom properties** -- variables declared in `:root` that are never referenced anywhere in the file. Use `grep -c "variable-name" index.html` to verify zero references before removing.
3. **Unused JavaScript functions** -- functions that are never called from HTML event handlers (onclick, onchange, etc.), other functions, or setTimeout/setInterval callbacks. Use `grep -n "functionName" index.html` to verify zero references (excluding the declaration itself) before removing.
4. **Unused JavaScript variables and state properties** -- declared but never read.
5. **Commented-out code blocks** -- remove entirely. This is a prototype, not a production codebase. Version history lives in Git, not in comments.

**Do not remove:**
- Code that appears unused but is referenced dynamically (e.g., function names constructed as strings, CSS classes applied via JavaScript variables)
- CSS for hover/focus/active states of elements that exist in the DOM
- Placeholder or empty-state rendering code, even if the current state does not trigger it

After this pass, report what you removed and the line count reduction.

## Pass 2: Inline Style Extraction

Inline styles that appear 3 or more times with identical or near-identical values should be extracted into named CSS classes. "Near-identical" means the same CSS properties with the same values, differing only in one property that can be handled as an override (e.g., three elements share `display:flex;align-items:center;gap:8px;padding:12px` but one has `padding:16px` instead).

**Process:**
1. Search all `style="..."` attributes in static HTML and all `style='...'` strings in JavaScript.
2. Group identical or near-identical style strings.
3. For each group of 3+, create a descriptive CSS class and replace the inline styles with that class.
4. Place new classes near related existing classes in the `<style>` block, not at the bottom of the stylesheet.

**Naming convention:** Use the existing naming patterns in the file. If the file uses BEM, follow BEM. If it uses utility-style names like `.flex-1`, follow that. If it uses semantic names like `.cost-card`, follow that. Do not introduce a new naming convention.

**Do not extract:**
- One-off inline styles that appear only once or twice
- Inline styles in JavaScript `html +=` strings where the style varies by state or data (e.g., conditional border-top on first vs. subsequent items)
- Layout-specific overrides like `style="flex:1"` on a single unique element

After this pass, report the number of classes created and the approximate line count impact.

---

## Pass 3: Duplication Consolidation

**This is the highest-risk pass. Be conservative.** Only consolidate patterns you are fully confident are functionally identical. When in doubt, leave duplication in place. Duplicated code in a prototype is an annoyance; a broken render function is a blocker.

Look for repeated patterns in the JavaScript rendering logic:

1. **Repeated HTML string construction** -- If two or more render functions build similar card layouts, list rows, or button groups, extract a shared helper function. Name it descriptively (e.g., `buildCardHeader`, `buildActionRow`).
2. **Repeated event handler patterns** -- If multiple elements wire up similar onclick/onchange handlers with only an ID or index differing, consolidate into a single parameterized function if one does not already exist.
3. **Repeated style object construction** -- If JavaScript builds the same style string in multiple places, extract it into a variable or helper.

**Do not consolidate:**
- Patterns that look similar but have subtle behavioral differences (different event handlers, different state dependencies)
- Code that is intentionally duplicated for clarity in a prototype context (e.g., separate render functions for each tab that happen to share some structure)

After this pass, report what you consolidated and the line count reduction.

---

## Pass 4: File Organization and Readability

1. **CSS ordering** -- Group related rules together with section comments. Suggested order: CSS custom properties / design tokens, reset/base styles, layout/structural, component classes, state/modifier classes, utility classes, media queries.
2. **JavaScript ordering** -- Group related functions together with section comments. Suggested order: state/data model, utility/helper functions, render functions, event handlers, initialization.
3. **Section comments** -- Use the existing comment style in the file (e.g., `// ===================== SECTION =====================`). Do not introduce a new comment convention.
4. **Consistent formatting** -- Normalize inconsistent indentation, spacing, and line breaks within each section. Do not reformat the entire file if most of it is consistent and only a few sections are messy.
5. **Magic numbers** -- If a numeric value (color, size, spacing) appears in inline styles or JavaScript and an existing CSS custom property holds that value, replace the magic number with the variable reference. Do not create new custom properties for this purpose.

## Output

After completing all four passes, provide:

1. **Line count report** -- Starting count, count after each pass, final count, and total reduction (lines and percentage).
2. **Change log** -- For each pass, a bulleted list of what was removed, extracted, consolidated, or reorganized. Be specific: name the CSS rules, functions, and classes affected.
3. **Risk areas** -- Any changes where you had less than full confidence that visual/behavioral parity was maintained. Flag these specifically so I can spot-check them.
4. **Suggestions not made** -- If you noticed structural improvements that would require visible changes (e.g., "the empty state pattern is inconsistent across panels"), note them here as future work without implementing them.
